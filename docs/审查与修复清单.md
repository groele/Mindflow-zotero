# MindFlow Zotero 5.0.0 数据链路审查与 5.0.1 修复清单

日期：2026-09-28。审查对象是本目录中的 5.0.0 插件实际运行脚本和打包前端，随后在本目录形成修正版。宿主脚本与 上游源码目录 的源文件、前端与其构建产物逐项核对过，初始 SHA-256 一致；前端源码复制到本目录的 `source/src` 后修改，未改动那个仓库。原插件、原 XPI 和原界面文件保存在 `backups/original-5.0.0-*`。

这次“选中 A 却打开 B”并非一个按钮错误，而是多个身份与生命周期问题叠加。以下错误都依据原代码确认；测试结果只证明下文覆盖的场景，没有把未运行的群组云同步、AI 服务商调用算作通过。

## 一、数据链路与错误传播

原来的链路：

```text
列表选择 / PDF 阅读器 / 右键菜单 / 条目侧栏
  → 解析父条目、枚举 .mindflow 附件
  → 寻找可复用标签或独立窗口
  → 初始参数 / 握手 / postMessage
  → 按 doc.id 查本地工作区，用 updatedAt 比较版本
  → 设置全局 active_doc_id，显示导图
  → 本地自动保存
  → 查找归档父条目、匹配已有附件、写文件、更新大纲
```

主要失效点：

1. `item.key` 在不同文献库之间不能作为全局身份，但原解析器跨库搜索，找到第一个就返回。
2. 标签匹配同时接受文档 ID、附件裸键和父文献；不同附件可能满足其中一个宽松条件。
3. Zotero 10 的 `_tabs` 记录不带内容容器。原消息代码取不到 iframe，标题代码随后回退到第一个 MindFlow 标签。
4. 前端将复制附件内保留的 `doc.id` 当作完整身份；另一个附件或文献的较新缓存便可能抢占显示。
5. 初始化效果依赖回调变化。设置加载、更新后重新运行时又加载全局最近文档，使已打开的 A 被 B 覆盖。
6. 归档阶段再次用选中状态、截短文件名等作为依据，导致错误关联有机会继续写回 Zotero。

修复后的链路：

```text
捕获明确条目或具体附件
  → 严格解析文献库范围 + 条目键
  → 用 attachment:<libraryID>:<attachmentKey> 匹配具体导图
  → 通过 Zotero 的 getTabContent 获取内容容器
  → 初始动作只消费一次；后续动作等待初始化并串行执行
  → 先核对具体附件来源，再比较同一来源的版本
  → 相同 doc.id / 不同来源：保留原图，为请求附件建立独立工作区 ID
  → 保存时检测修订号；归档时使用明确关联与来源附件
  → 校验父子关系、文献库、附件登记和真实文件回读
  → 成功后保存来源附件身份，并更新所属标签/窗口的路由
```

身份规则：文献使用文献库范围和 item key；附件使用 libraryID + attachment key；分类使用 libraryID + collection key；专题使用排序后的各项 libraryID + key；本地 doc.id 只标识工作区文档。标题和文件名只用于显示。

## 二、逐项错误清单与修复

优先级：P0 表示可能串图、误写或丢失编辑；P1 表示重要交互、启动或保存可靠性错误；P2 表示界面要求或可用性改进。表中的“已修复”指代码已落实；覆盖证据在第三节区分。

## 三、验证记录与边界

### 自动回归

- 宿主：`node --test scripts/test-host.mjs`，21 项通过。覆盖明确库范围、歧义键、数字 key、同父多图、跨库附件、真实 Zotero 标签记录形状、读取范围、消息归属、损坏数据、错误归档目标、更新失败、写后损坏、并发归档与过时修订。
- 前端数据服务：`source/node_modules/.bin/vite-node.cmd source/tests/test-zotero.ts`，13 项通过。覆盖跨来源缓存、同库/跨库身份、旧版来源不确定、版本选择、独立副本、直接解析、工作区 ID 检验、关闭后按来源恢复、重复来源歧义和并发本地修订冲突。
- 构建：`node scripts/build-local.mjs`，TypeScript 检查、生产 IIFE 构建、四个 JavaScript 语法检查通过。
- 原版宿主在同一测试框架的输出单独保存在 `original-host-test-results.txt`。其中有新增测试接口缺失导致的失败，不应把总失败数当作独立缺陷数。

### 真实桌面验证

通过 `scripts/start-native-test.ps1` 从最终 5.0.1 XPI 提取插件，加入仅用于测试的启动检查脚本后，在独立配置的真实 Zotero 10.0.3 内运行，并实际创建测试文献、导图附件与工作区文件。使用独立 `tests/native-test-*/data`，测试前检查目录隔离；没有写入用户现有文献库。最终 12 项均通过。

测试检查真实 iframe DOM、原生标签数据、数据库登记的附件父条目及真实落盘文件。最终结果见 `native-regression-results.json`，包括：

1. 打开 A 的准确附件。
2. 同文档 ID 的 B 显示 B，A 内容不被覆盖。
3. 设置更新不把 A 恢复成全局最近打开的 B。
4. 修改 A 标题后 A→B→A 重开保留编辑。
5. 原生与工作台图标旁品牌文字移除。
6. 关闭重开 B 复用原隔离工作区 ID。
7. 同一文献强制新建两份图，并等待归档完成。
8. 真实附件内容和父条目一致。
9. 同一文献的多份附件打开不同准确标签。
10. 独立窗口 A/B 保持不同来源，重复打开 A 复用其窗口。
11. 原生条目侧栏注册存在，图标仍具有辅助技术名称。
12. 原生 1000px 窗口的标题、编辑按钮与工具按钮区域不重叠。

首次新增导图原生测试曾过早检查附件数量；修改为等待真实归档完成后重测。独立窗口测试实际暴露 API 未连接问题，随后修复后重新验证。中间失败记录留在测试目录，最终报告只对应最终构建。

本轮没有验证：用户现有资料库里历史错误关联的逐份迁移、真正群组服务器/跨设备同步、真实 PDF 阅读器点击全过程、真实第三方 AI 网络调用。跨库同键与阅读器目标判定通过宿主回归覆盖；这不等于云同步或阅读器完整交互测试。

## 四、交付与后续核对

- 修正版：根目录 `mindflow-zotero-5.0.1.xpi`。
- 可编辑前端：`source/src`；宿主仍在原来的 `chrome/content/scripts`。
- 验证记录：本目录的宿主、前端、原生测试结果，以及 `package-verification.json`。
- 安装：Zotero → 工具 → 插件 → 从文件安装插件，选择 5.0.1 XPI；安装后重启 Zotero使旧脚本及既有标签实例退出。
- 这是本地修复包，未推送 GitHub、未创建远端 Release。远端更新描述文件没有伪造一个未发布的下载地址。
- `source/node_modules` 当前复用本机 上游依赖目录 的依赖目录。构建不会修改那份源码；搬迁项目后需在 `source` 安装 lockfile 对应依赖。

对于以前已串图的文件，建议先备份，再根据具体附件父条目与内容核对归属。新代码在来源不明确时隔离或报错，不会按相同标题强行合并。若发现“同一附件关联多份本地导图”的提示，可在工作区保留需要的版本，把其他版本作为解除关联的独立副本处理。
